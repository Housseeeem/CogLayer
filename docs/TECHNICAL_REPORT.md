# CogLayer: Technical Report
## IEEE CIS TAC CISTAC 1.0 — AI4Brain Challenge, "Cognitive Growth Agent" Track

---

## 1. Summary

CogLayer is a provider-agnostic cognitive coaching layer that sits between a user and
any large language model. It runs the loop Assess → Understand → Coach → Improve across
four observable cognitive dimensions using eight keyboard-and-mouse tasks, with no
camera or microphone input. After each completed session it updates an uncertainty-aware
Bayesian profile, generates supportive text feedback, and displays progress through a
radar chart, progress curves, a performance heatmap, and a daily task plan. CogLayer is
non-clinical: it does not perform any medical or clinical evaluation, and none of its
outputs constitutes a diagnosis or a standardised test score. All measurements come from
interaction timing and response accuracy only.

---

## 2. Problem and Approach

Users who work daily with large language models accumulate habits — some effective, some
not — with little structured feedback on how well they actually reason, remember context,
or verify information. A raw conversation history is too noisy and too private to analyse
directly; what is needed is a layer that extracts lightweight behavioural signals without
storing message content, builds an evolving profile of cognitive performance tendencies,
and converts that profile into actionable coaching.

CogLayer implements that idea as four cooperating layers.

**Layer A** collects signals through short interactive tasks that run in the browser.
Timing and accuracy are captured client-side with `performance.now()` (sub-10 ms
resolution) and submitted to a REST API.

**Layer B** maintains a Beta(α, β) posterior per user and dimension. Every submitted task
updates the relevant dimension; the model reports a posterior mean and a 90 % credible
interval. A forgetting factor (λ = 0.98) shrinks the posterior toward the uniform prior
between sessions so that stale evidence loses influence over time.

**Layer C** builds coaching feedback from the profile. A local text summary is
constructed from the credible intervals; when a provider is configured and the
`coach_use_llm` flag is enabled, this summary (never the profile object) is sent to the
provider with a neutral instruction. The resulting text goes through a forbidden-word
filter before reaching the user. The dashboard renders three chart types from the stored
profile history. The Cognitive Lab screen (screen 3) shows a daily recommended session
generated by a separate adaptive selector.

The **AI Collaboration Score** is a separate experimental module that records explicit
behavioural observations across five components of human-AI collaboration and computes a
fixed-weight aggregate.

## 3. Layer A: Assessment and Profile

### 3.1 Dimensions and tasks

CogLayer defines four active cognitive dimensions measured by eight tasks. The table
below is derived directly from `docs/DIMENSIONS.md`, which documents the live registry
built by `build_default_registry()` in `src/coglayer/signals/registry.py`.

| task_id | Dimension | Outcome metric | Weight | Count metric |
|---|---|---|---|---|
| `go_no_go` | `response_inhibition` | `nogo_accuracy` | 1.0 | `nogo_valid_count` |
| `sequence_span` | `sequential_visual_memory` | `correct_sequences_ratio` | 1.0 | `valid_sequence_count` |
| `corsi_blocks` | `sequential_visual_memory` | `accuracy` | 1.0 | `valid_sequences_count` |
| `digit_span` | `working_memory` | `accuracy` | 1.0 | `valid_trials_count` |
| `n_back` | `working_memory` | `n_back_accuracy` | 1.0 | `valid_trials_count` |
| `letter_number_sequencing` | `working_memory` | `accuracy` | 1.0 | `valid_trials_count` |
| `stroop` | `cognitive_flexibility` | `incongruent_accuracy` | 1.0 | `valid_trials_count` |
| `perception_lab` | `cognitive_flexibility` | `perceptual_stability` | 1.0 | `valid_trials_count` |

All outcome metrics are in [0, 1]. Each task contributes one Evidence record to the
dimension's Bayesian posterior.

### 3.2 Beta posterior with forgetting factor and 90 % credible interval

The profile model is in `src/coglayer/profile/model.py`. The constants defined there are:

```
DEFAULT_FORGETTING_FACTOR = 0.98
MAX_PSEUDO_COUNT = 20.0
```

The update sequence for each evidence submission is:

1. **Forgetting.** Shrink the posterior toward the uniform prior Beta(1, 1):
   `α' = 1 + (α − 1) × 0.98`, `β' = 1 + (β − 1) × 0.98`.
2. **Effective count.** `n_eff = weight × min(count, 20)`. This caps the influence of
   any single session at 20 pseudo-observations.
3. **Bayesian update.** `α += n_eff × outcome`, `β += n_eff × (1 − outcome)`.
4. **Credible interval.** `lower = Beta.ppf(0.05, α, β)`,
   `upper = Beta.ppf(0.95, α, β)` (from `scipy.stats.beta`).

If `count == 0` the entire update is skipped; no forgetting is applied and no Evidence
record is appended. The model exposes `get_state` to persist (α, β) across sessions and
`seed_dimension` to reconstruct from stored values without lossy method-of-moments.

### 3.3 Data-quality gate

Before marking a session complete, the `AdaptiveDecisionEngine` checks that each
submitted task meets a completeness threshold (≥ 0.80, `completeness_threshold: float =
0.8` in `src/coglayer/core/settings.py` line 41). Tasks that fall below this threshold
are not counted toward session completion. For the Go/No-Go task specifically, a second
quality gate applies: the scorer requires a minimum Go accuracy of 0.70
(`go_no_go_min_go_accuracy: float = 0.7`, `src/coglayer/core/settings.py` line 50)
before the profile update proceeds. This 0.70 threshold is a design choice and is not taken from a published source. The `data_quality` table records `completeness`,
`valid_trials`, and `total_trials` per (session, task). Anticipation responses below
100 ms are excluded from Go/No-Go and N-back scoring; responses above the task-specific
timeout (30 000 ms for span tasks, 3 000 ms for N-back, 3 000 ms for Stroop) are marked
invalid.

### 3.4 Brain Twin variation flag and profile history

The Brain Twin module (`src/coglayer/core/brain_twin.py`) maintains an exponential
moving-average baseline per user over comparable Go/No-Go outcomes. Once enough
observations are available, it emits a `BrainTwinState.VARIATION_FLAGGED` signal when
the current result diverges from that baseline. The dashboard page view
(`src/coglayer/ui/page_views/dashboard.py`) renders a "Brain Twin Fast-Track" section
with a caption: "A transparent baseline for comparable Go / No-Go outcomes. A flag means
variation worth reviewing, not a cause or conclusion." When a flag is present, the UI
displays a warning inviting the user to review the context or repeat the activity.

Profile history is surfaced through three elements on the same dashboard screen (screen
4, `render_dashboard_page`): the longitudinal progress curves showing raw outcomes per
dimension across sessions, the performance heatmap showing the mean outcome per
(dimension × session) cell, and the Assessment History table listing every evidence
record in reverse chronological order. There is no dedicated Brain Twin history screen.

### 3.5 Non-biometric mode

All measurements come from keyboard and mouse interaction only. No camera, microphone,
or biometric sensor is used anywhere in the codebase. `docs/DIMENSIONS.md` states this
explicitly: "No camera or microphone input is used in the MVP. Every measurement comes
from keyboard/mouse interaction only."

## 4. Layer B: Coach

### 4.1 Two surfaces

The coaching module has two distinct surfaces (documented in `README.md` and
`src/coglayer/coach/coach.py`):

- **Feedback summary** (`POST /v1/assessment/coach/{user_id}`): builds a local text
  summary from credible intervals and session counts, then optionally sends it to a
  provider for rewriting. This path always returns text; there is no fallback error
  message when no provider is configured.
- **Conversation chat** (`POST /v1/assessment/coach/{user_id}/conversations/{id}/messages`):
  a multi-turn chat interface. Without `coach_use_llm = true` and a valid provider, every
  reply is the fixed fallback: "The conversation service is temporarily unavailable.
  Please try again later."

### 4.2 Local text first

`CognitiveCoach.generate_feedback` in `src/coglayer/coach/coach.py` always builds
a local summary before consulting a provider. If `settings.coach_use_llm` is `False`
or `provider is None`, it returns the local text directly. The provider is only called
when both conditions are met; the `CognitiveProfile` object is never included in the
prompt, only the local summary string is sent.

### 4.3 Forbidden-word filter

The `validate_llm_reply` function in `src/coglayer/coach/coach.py` rejects any provider
response that contains the following words as whole-word, case-insensitive matches:
`diagnosis`, `disorder`, `deficit`, `impairment`, `IQ`, `patient`, `patients`. A
rejected response causes the coach to fall back to the local text and log a warning
without including the text content in the log. The response is also rejected if it is
shorter than 20 characters after stripping or if it echoes the system instruction.

### 4.4 What the provider receives

The prompt sent to the provider is constructed in `coach.py` as:

```python
prompt = f"{system_instruction}\n\n{local_text}"
```

where `local_text` is the locally-generated summary and `system_instruction` is the
constant `_LLM_INSTRUCTION`: "You are a supportive cognitive coach. Use the following
notes to write friendly, encouraging feedback for the user. Do not rank dimensions
against each other and do not produce a global score. Keep it concise."

The `CognitiveProfile` object is never passed to the provider. This is enforced at the
architecture level: the profile is consumed inside `coglayer` only, and `coglayer.ui`
communicates with `coglayer.api` over HTTP, never importing domain modules directly
(`docs/ARCHITECTURE.md`, Contract d).

## 5. Layer C: Dashboard

The dashboard is implemented in `src/coglayer/ui/dashboard.py` using Altair, and
rendered by `src/coglayer/ui/page_views/dashboard.py` (screen 4, "Cognitive Profile &
Dashboard"). The daily recommended session is a separate feature rendered in screen 3
("Cognitive Lab"), described below.

**Brain Twin status.** The dashboard opens with a "Brain Twin Fast-Track" section (from
`_render_brain_twin` in `src/coglayer/ui/page_views/dashboard.py`) showing the current
variation flag for comparable Go/No-Go outcomes. No variation history chart is shown;
the flag is present or absent based on the latest available EMA signal.

**Radar chart.** `create_radar_chart` renders four dimensions as polygon layers: an
upper credible-interval boundary (blue dashed), a lower boundary (red dashed), and a
posterior mean polygon (solid blue). Four grid rings at 0.25, 0.50, 0.75, and 1.00
provide reference. When fewer than three dimensions have data, the radar degrades to a
horizontal interval chart (`create_interval_chart`).

[SCREENSHOT: radar_chart]

**Progress curves.** `build_progress_curve_data` extracts the chronologically ordered
outcome series per dimension from the evidence history. `create_progress_curve` renders
one line per dimension (session index on x, outcome in [0, 1] on y) with distinct colour
and dash patterns. Integer tick marks on the x-axis prevent fractional session labels.

[SCREENSHOT: progress_curves]

**Performance heatmap.** `build_heatmap_data` groups evidence records by (session_id,
dimension), assigns chronological session labels ("1", "2", …), and computes the mean
outcome per cell. `create_heatmap` renders this as an Altair rect chart with a blues
colour scale fixed to [0, 1] and the numeric mean displayed inside each cell. Rows are
cognitive dimensions; columns are session numbers in chronological order.

[SCREENSHOT: performance_heatmap]

**Assessment History table.** `build_history_rows` returns evidence records sorted most
recent first; the dashboard renders them as a `st.dataframe` with columns Session, Task,
Dimension, Outcome Score, and Timestamp.

**Daily recommended session (Cognitive Lab, screen 3).** The `AdaptiveGameSelector` in
`src/coglayer/coach/selector.py` generates 2 or 3 recommended tasks per day, stored in
`AdaptiveDailyPlan`. It is rendered by `render_cognitive_lab_page` in
`src/coglayer/ui/page_views/cognitive_lab.py` under the subheader "Daily recommended
session". Selection uses a deterministic seed derived from `sha256(user_id:plan_date)`.
The selector operates in three modes based on history availability: (a) no history —
starts from a default introductory trio (`go_no_go`, `digit_span`, `stroop`) and fills
remaining slots by dimension diversity, recorded as `factors_used:
["initial_diversity", "introductory_baseline"]`; (b) low-quality history (all results
below 0.50 completeness) — selects by dimension diversity, `fallback_strategy:
"data_sufficiency_fallback"`; (c) history available — a scored selection weighted by
`history_performance`, `diversity`, `recency_prevention` (−6 points if a task appeared
in the most recent completed session), `user_preference`, `brain_twin_variation_adjustment`
(+8 to Go/No-Go when a variation is flagged), `subjective_fatigue_adaptation`, and
guidance-level factors. The user may also signal fatigue via a "Slightly Fatigued" selectbox,
which sets difficulty to "introductory" for all chosen tasks.

## 6. AI Collaboration Score

The AI Collaboration Score is an experimental measure defined in
`src/coglayer/core/ioi.py`. It is separate from the cognitive assessment battery.

### 6.1 Components and weights

The constant `IOI_WEIGHTS` in `ioi.py` defines exactly:

| Component | Enum value | Weight |
|---|---|---|
| Critical verification | `CRITICAL_VERIFICATION` | 0.25 |
| Clarification | `CLARIFICATION` | 0.20 |
| Iteration | `ITERATION` | 0.20 |
| Autonomy | `AUTONOMY` | 0.20 |
| Responsible use | `RESPONSIBLE_USAGE` | 0.15 |

The weights sum to 1.0; a `RuntimeError` is raised at module load time if they do not.

### 6.2 Scale

The aggregate score is a proportion in [0, 1]. The UI multiplies by 100 to display it
as `x / 100` (for example, `72.3 / 100`). It is not a 0–100 integer internally.

### 6.3 Minimum observations

The constant `IOI_MINIMUM_OBSERVATIONS = 3` in `ioi.py` is the per-component threshold.
The aggregate is computed only when all five components each have at least three valid,
deduplicated observations. Until that condition is met, `IOIScore.status` is
`"INSUFFICIENT_EVIDENCE"` and `aggregate_score` is `None`. Deduplication keeps only the
first observation per `(component, opportunity_id)` pair; later submissions for the same
pair are silently ignored.

### 6.4 Experimental status

The IOI score has not been validated against independent measures of human-AI
collaboration quality. The weights, component definitions, and minimum-observations
threshold are design choices matching the challenge brief, not empirically derived
parameters. `IOIScore.calculation_version` is fixed at `"1.0"` to allow future
recomputation of historical scores if the formula changes.

## 7. Explainability and Safety

### 7.1 Consent

Consent is recorded by `ConsentService` in `src/coglayer/privacy/consent.py`.
`POST /v1/assessment/sessions` calls `has_consented` and returns HTTP 403 if no active
consent record exists. The consent screen states what is stored, what is sent to the
provider, and that the tool is non-clinical. Guardian consent fields are available for
minors.

### 7.2 Deletion endpoint

`DELETE /v1/assessment/users/{user_id}` in `src/coglayer/api/routers/admin.py` removes
all rows across every table for the given user: sessions, trials, task metrics, data
quality, collaboration events (via `ON DELETE CASCADE`), profiles, consent, coaching
conversations, coaching messages, experience profiles, and daily plans. On success it
returns HTTP 204. The deletion is covered by tests in `tests/unit/test_storage.py` and
`tests/unit/test_storage_property.py`.

### 7.3 What is stored

The following are persisted to the SQLite database:

- Session metadata (session ID, user ID, status, timestamps, completed task list).
- Per-trial structured data: stimulus identity, expected response, actual response,
  reaction time, validity flag, invalidity reason. This is not free-text.
- Aggregated task metrics: accuracy, span lengths, reaction times.
- Data quality indicators: valid trial counts, completeness ratio.
- Cognitive profile: serialised Bayesian parameters (α, β), posterior mean, credible
  interval, evidence count, and last-update timestamp — no raw message text.
- Collaboration events: structured IOI component observations, no message text.
- Experience profile: onboarding answers (age group, goals, preferences).
- Coaching conversation text: the `content` column of `coach_messages` stores the text
  of each coaching turn. **This is an exception to the derived-indicators-only rule.**

### 7.4 Non-clinical wording

The forbidden-word list in `src/coglayer/coach/coach.py` (`diagnosis`, `disorder`,
`deficit`, `impairment`, `IQ`, `patient`, `patients`) applies to all provider responses.
The coaching feedback always appends the fixed disclaimer: "Based on the tasks completed
so far — not a clinical assessment." The architecture rules in `AGENTS.md` prohibit these
words in code comments, documentation, UI strings, and commit messages.

### 7.5 No decision based on face or voice

No camera or microphone code exists in the codebase. All signals come from keyboard and
mouse timing and accuracy as recorded by browser `performance.now()`.

### 7.6 Gaps (stated honestly)

Three gaps exist relative to `docs/SPEC.md`:

1. **Automatic retention purge not implemented.** There is no scheduled job,
   background task, cron entry, or database trigger that purges expired records.
   Data persists locally in SQLite until explicitly deleted through the endpoint above.
2. **Coach message text storage is configurable.** The `coach_messages.content`
   column stores the text of each coaching turn ONLY when
   `COGLAYER_STORE_CONVERSATIONS=true` (default: `false`). When disabled, messages
   stay in process memory only.
3. **Identity declared, not authenticated.** The user identifier is a string entered in
   the Streamlit sidebar. There is no authentication layer; the application has no
   mechanism to verify that the declared identity matches the person at the keyboard
   (`README.md`, Known limitations).

## 8. Evaluation

### 8.1 Test suite

The following command was run once:

```
uv run pytest --no-cov -q
```

Result:

```
644 passed, 1 warning in 180.47s (0:03:00)
```

The warning is a third-party deprecation notice from `starlette.testclient` about
`httpx`; it does not affect any test result.

Tests are organised in three tiers:

- **Unit tests** (`tests/unit/`): zero network calls, use `FakeProvider` for
  deterministic LLM responses, verify exact scorer arithmetic and coach-lock mechanics.
- **Property-based tests** (using `hypothesis`): validate mathematical invariants across
  hundreds of generated inputs — probabilities stay in [0, 1], intervals contain the
  mean, adding evidence never widens the interval beyond the prior, the forgetting factor
  keeps α ≥ 1 and β ≥ 1, completeness stays in [0, 1], anticipation exclusion is
  invariant to trial order, and `delete_user` removes all rows across all tables.
- **Integration tests** (`tests/integration/`): exercise full API flows end-to-end with
  FastAPI `TestClient` and isolated SQLite databases, covering all named acceptance
  criteria.

Coverage targets: ≥ 85 % overall, ≥ 95 % for `profile` and `coach` (currently 100 %
for both, per `docs/ARCHITECTURE.md`).

No accuracy numbers from simulated users are reported here because the simulator
evaluation described in `docs/SPEC.md` section 10 was not run against the full test
battery. Reporting invented numbers is outside scope.

### 8.2 Architecture contracts

`import-linter` enforces four contracts at every `make check` run:

- **Contract (a):** `coglayer.core` imports nothing from any other project module.
- **Contract (b):** Domain modules (`signals`, `profile`, `coach`, `privacy`,
  `providers`, `exercises`, `sim`) import only from `core`; they never import each other.
- **Contract (c):** Domain modules never import from the composition layer.
- **Contract (d):** `coglayer.ui` communicates with `coglayer.api` only over HTTP via
  `httpx`; it never imports domain modules directly.

The full quality gate (`make check`) runs in order: `ruff format --check`, `ruff check`,
`mypy --strict`, `import-linter`, `pytest` with the 85 % coverage threshold, `gitleaks`,
and `pip-audit`. The same sequence runs in CI on every push and pull request.

## 9. Limitations and Next Steps

The following limitations are present in the current codebase and are stated without
qualification.

**Goal tracking not displayed.** The `daily_plans` table stores a generated task
sequence but there is no UI panel that tracks completion of goals across multiple days or
shows a learning-path progression across the full task battery.

**Two dimensions not implemented.** `logical_reasoning` and `critical_thinking` appear
in `docs/SPEC.md` section 4 as intended MVP dimensions. `docs/DIMENSIONS.md` confirms:
"no task, scorer, or registry entry in the current code." The extension mechanism is in
place — adding a dimension requires a new scorer class, a registry entry, and a UI
component without touching existing modules — but no implementation exists yet.

**One task per dimension per session in the demo.** The demo data script
(`scripts/demo_simulation.py`) creates 6 sessions for `demo_user_001` with 4 tasks per
session, covering all 8 tasks across sessions. The Streamlit UI currently offers one
task per dimension per assessment session in the interactive path. Users who want to
contribute data from all eight tasks must complete multiple sessions.

**Practice effects.** All eight tasks are susceptible to performance improvement with
familiarity. The forgetting factor (λ = 0.98) reduces the weight of stale evidence but
does not distinguish genuine improvement from practice-related gains. This is documented
for each task in `docs/DIMENSIONS.md`.

**Differing scales across tasks.** Tasks within the same dimension have different
response distributions and ceiling/floor effects. `working_memory` pools three paradigms
(digit span, N-back, letter-number sequencing) under a single Beta posterior, which
inflates noise when the paradigms produce systematically different accuracy levels.
Similarly, `perceptual_stability` in `cognitive_flexibility` is computed as
`max(0, 1 − switch_rate / 30)`, where the constant 30 is a design hypothesis not
derived from normative data (`docs/DIMENSIONS.md`, section 4).

## 10. Reproducibility

All commands below assume the repository is cloned and dependencies are installed with
`make install` (which runs `uv sync --all-extras` and installs pre-commit hooks).

### Run the API

```
uv run uvicorn coglayer.api.app:app --port 8000
```

### Run the UI

```
uv run streamlit run src/coglayer/ui/app.py
```

The UI expects the API at `http://localhost:8000` by default. Override with the
`COGLAYER_API_URL` environment variable.

### Run the demo data script

The script requires a running API. It creates 6 assessment sessions for the synthetic
user `demo_user_001` (4 tasks per session, all 8 tasks covered) and prints
`SIMULATED DEMO DATA` with a profile summary to the console.

```
uv run python scripts/demo_simulation.py --api-url http://localhost:8000
```

### Run the tests

```
uv run pytest --no-cov -q
```

Drop `--no-cov` to produce a coverage report (85 % overall threshold, 95 % for
`profile` and `coach`).

### Environment variables

Provider API keys come from environment variables only. Copy `.env.example` to `.env`
and fill in the relevant keys. The `.env` file is git-ignored. No secret should ever be
committed to the repository.
